**E2E green and direct function execution are complementary, not redundant**

- A full E2E suite of 145 checks passed, yet the blind reviewer — executing the pure functions directly instead of driving the UI — found one blocker (a wrongful hard veto on a legitimate input) plus two scoring majors (dead no-data inputs silently flipping scores; a classifier contradicting its own documented contract).
- A passing E2E suite proves the happy paths; direct execution of the logic under review proves the logic. Both angles are needed; neither substitutes for the other.

**Rework needs re-verification, always — including the fix for the fix**

- The polish pass after the reviewer's ALLOW introduced a real regression (a blunt submit throttle that swallowed legitimate fast-but-distinct submits); the full-suite re-run caught it with 9 failures. Narrowing the throttle fixed that but introduced a second defect in the same class (follow-up re-answers swallowed), which QA caught again.
- Two "fix → re-verify" rounds were needed for a single review finding. Containment, now a runtime convention: every post-ALLOW edit gets a full-suite re-run, and the re-run's own fix gets the same treatment — the verification loop only closes on a clean run.

**Commit-identity failures recur in new variants (FC-006, occurrence 2)**

- A push to a platform-built branch was rejected because the push identity's email was private on the account ("email privacy restrictions") — a new variant of the deploy-identity failure class first recorded last run (a bot identity the deploy platform did not recognize).
- Workaround: push under the noreply identity that still attributes to the human's account, so the platform preview built fine. The durable fix is the human toggling the account's "block command line pushes that expose my email" setting.
- Containment, extending the FC-006 convention: before pushing to any platform-built branch, confirm the push identity passes the account's email-privacy setting, and keep the per-repo record of which identities deploy cleanly — now covering both the bot-identity and the email-privacy variants.

**Document QA contracts where the code lives, so reviewers can execute them**

- The modules carried "QA contracts" in prose (documented input/output expectations for the parsing and scoring functions). The blind re-reviewer executed those contracts directly and verified every pair empirically.
- A behavioral contract written in the module's own prose turns a reviewer's spot-check into a complete verification plan. Contracts belong in the code, not just the report.

**Governance self-audit (every-run backstop check)**

- The single deliverable presented to the human today (immersive demo rewrite, preview branch) carries a recorded blind-review ALLOW on its verdict ticket (`~/workspace/governance-tools/runs/verdicts.jsonl`). No deliverable presented without a recorded ALLOW. Zero governance misses today.
