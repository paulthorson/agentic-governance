## Proposal: UX domain must require flows, JTBD job stories, and research validation

**Problem.** The UX constitution (`constitution/domains/ux.md`) enforces four
mechanical rules — customer vetoes, genuine options, engineering-ease
disclosure, business-goal linkage — all checked against the decision record.
What it never requires is evidence that the worker understood the user before
designing: no user flows for key journeys, no Jobs-To-Be-Done grounding, no
mapping of decisions to existing research. A blind reviewer can therefore
ALLOW a polished artifact that was never validated against how users actually
work. In a live design-system monorepo build (tokens, web components,
terminal theme, docs), this gap surfaced in practice: the human operator had
to stop the build and explicitly demand user flows, a JTBD framework, and
validation against the project's research before UX work could be trusted.

**Proposal.** Add a standing UX-domain check, in the mechanical style of the
existing rules:

1. **User flows are mandatory artifacts.** Every UX-domain work product must
   include flows for its key journeys (e.g., adoption, theming,
   contribution). A submission with no flows fails the check and goes back
   to the worker — the same shape as Rule 2's options requirement.
2. **JTBD job stories ground every major decision.** Each significant UX
   decision carries a job story (situation, motivation, expected outcome).
   The mechanical check: a story of the form "when [situation], I want
   [motivation], so I can [outcome]" that a reviewer can falsify. Stories
   that restate the feature ("so the UI is nicer") fail, mirroring Rule 4's
   rejection of vague business goals.
3. **Research validation is explicit.** Every flow and job story maps to
   supporting or contradicting research findings. Where no research exists,
   the entry says so explicitly and routes to the human gate rather than
   inventing grounding — the same honesty pattern Rule 4 uses for missing
   metrics.

**Why this shape.** It reuses the constitution's existing machinery
(mechanical checks, explicit-unknown routing, KICK_BACK on missing
artifacts) instead of adding guideline prose. Reviewers get something
falsifiable to judge, and workers cannot pass UX review on craft alone.

**Scope note.** This is intake, not an amendment: the constitution itself is
untouched. The maintainer decides whether this becomes a Rule 5 candidate, a
standing constraint, or review-prompt guidance.
