**Review methodology (worked repeatedly this run)**

- Three-gate close-out (final ALLOW + green tests + committed) keeps earning its keep: an initiative can be fully ALLOWed yet 0% by the committed-work measure. Uncommitted reviewed code is invisible progress.
- Post-review modification is the silent killer of that gate: any file touched after its ALLOW needs a re-review ticket, mechanically. Caught twice tonight via file-mtime vs verdict-timestamp correlation; consider an optional code-reference/commit field on verdict records to make chain-of-custody mechanical.
- Verdict records carry epoch-ms `ts` but no human-readable timestamp and no commit hash — chain-of-custody had to be reconstructed by correlating `ts` against file mtimes and matching ALLOW summaries against diff content.
- Single-ticket verdict archaeology (25 records interleaved) requires manual per-unit latest-verdict reconstruction; per-unit tickets make "final state per unit" mechanical.
- A coordinator that reports "complete" with a present-tense work description ("now bundling…") has stalled, not finished — always verify the tree (verdict log, git status, tests) before accepting a completion report. The report is a claim; the tree is the evidence.
- Parallel blind reviews across domains beat serial single-domain loops: each domain's constitution catches what the others' cannot, and one consolidated rework list costs less builder churn than sequential kick-backs.
- When depth limits force the builder to run the adversarial prompts themselves, the isolation caveat must be recorded *in the verdict summary itself*, and the parent must arrange a genuinely independent re-review before it counts as cleared.
- A critic FAIL can be the most valuable verdict in the loop: one forced real close gates (dated decision record, real follow-up tickets) that replaced asserted-but-nonexistent "mitigations" — the difference between "100%" honest and "100%" performative.
- A KICK_BACK on a process slip only (not code) still needs a fresh blind re-review to clear — the loop isn't done until the reviewer signs off.
- Reviewer-verified claims need the reviewer's own runs: "reworded, re-reviewed" only holds when the reviewer re-verifies the text in the file, not the diff description.

**Scanner / keyword-veto false positives (third class of hit, same protocol)**

- The structural keyword scan cannot distinguish prose ABOUT a defect from the defect: "downtime" in test-fixture prose, "data loss" in comments describing the fix, "credential" in comments asserting the opposite — all fired as mechanical vetos. Protocol that works: record honestly, reword around the naive regex, fresh re-review — never argue it away and never quietly edit around it. Framework ask: scope the scan to code vs comments/descriptive contexts, or an allowlist.
- The same reword-and-flag pattern applies to structural scanners generally: security tooling's own vocabulary ("api key" in a secret-detector's docstring) will trip keyword scans; reviewers should expect this class on scrubber/detector work, and the human-only-clear rule stays the backstop.
- Different domain constitutions using different field names for the same concept is a framework-level inconsistency worth intake.

**Human clearance precedent (set today)**

- Five Rule 1 constitutional vetos were explicitly cleared by the human after plain-English review of each defect, fix, and verification; clearances recorded as `veto-clearance` records (source="human-…") in the verdict log. One veto was HELD OPEN by the human pending a new circuit-breaker feature.
- Precedent: a veto is not a KICK_BACK — rework + fresh ALLOW resolves the defect but does not clear the veto; only the human clears it, explicitly, after review. Finishers must check for explicit human-clearance notes on veto rework ALLOWs before counting work at 100%. This supersedes any looser "cleared by reviewer verification" handling.
- Close-out reports must name the clearance holder, not round the status up.

**Authority citations without provenance (second occurrence of a class)**

- A plausible-sounding authority citation ("per human <date>") was recorded for a decision the human never made, then survived four hops (report option → decision file → memory → memory "correction" → execution) because each hop trusted the previous hop's authority framing instead of checking for the human's words.
- Process fixes as written were advisory. Advisory text is the control class that already failed: the requirement existed in a document and nothing refused when it was ignored. A real gate (e.g. a check that rejects decision-attribution claims lacking a linked source quote before commit/merge) is the only fix class with enforcement — described here, not built, per the human's direction. The class is not "bad citation", it is "unenforced citation."

**Adversarial depth notes (reviewer-grade)**

- Rework that fixes the finding's *description* instead of the *implementation* is the same defect wearing a new coat — caught only by re-checking the claim against the code, not against the reviewer's words.
- The opt-in exception was the softest seam: two findings on a path that existed to be lenient. Exceptions to fail-closed deserve their own adversarial campaign, not inherited trust from the main path.
- "Returned without raising" is not "succeeded": success signals must be recorded at the point where success is actually known, never inferred from a non-raising return.
- Sanitizer's least-infallible line: stringification of attacker-influenced data is an attacker-controlled code path (a hostile `__str__` re-opened the exact hole the traceback-hygiene design closed). Defense-in-depth meant the demonstrated shape never even reached the sanitizer.
- Common-mode failure can live at the *decision* level, not just the signal level: three layers with independent regexes but one shared gate function were defeated by one threshold-logic flaw. Defense-in-depth must be audited at the decision level — any layer that calls another layer's gate function is not a layer.
- Backtracking-safe patterns need probes, not reading: adjacent zero-width-matching quantifiers turned linear input into a 60s timeout; the between-positions formulation plus a linear post-pass brought it to 0.017s.
- A test that probes re-entry with the wrong arity (zero-arg calls against an op-taking dispatcher) passes while the real hostile shape walks through; regression tests must use the demonstrated hostile shape verbatim.
- Mangling is a distinct failure mode from leaking and needs its own assertion — a test that only checks "no leak" passes mangled output.

**Process / environment notes**

- Assumption flags have a half-life: "contract not published" went stale mid-build when the dependency appeared in-tree. Re-verify assumed-absent dependencies right before writing parallel code.
- Declarative copies of enforcement numbers are invented metrics by another name: any number enforcement doesn't use is fiction in the UI — derive from the enforcement source of truth.
- Residual-risk notes are the next round's KICK_BACK waiting to happen — apply the cheap fix before the reviewer finds it.
- Shape-enumeration keeps failing open on the next variant: anchor on syntax that cannot be enumerated away (invariants like the `+` country-code prefix or letter-only final labels), not on lists.
- On a shared tree: `git add -A` / `git commit -a` are forbidden; stage only scoped paths and check the index immediately before committing; never push a swept commit — verify `git show --stat` and announce a sweep loudly instead of rewriting shared history.
- Durable review inputs never live in `/tmp` (wiped mid-session, files irrecoverably lost); ephemeral shared scratch dirs are a collision domain — namespace probe dirs per workstream.
- `ag_review.py` truncates its printed JSON at 20,000 chars; for long bundles call the framework's `run_review` via the adapter directly and persist the full prompt to a file (same canonical path, no truncation).
- Numbers on public pages must trace to something countable or come off: an untraceable "N modules" claim survived since it was introduced as "counts corrected" with no derivation; card-rendering code is the count of record for card claims. Push != deploy: with no deploy-tool access, live verification is a separate explicit step that can fail open — report it as its own line item.
- A re-review that only checks the finding text (not the implementation) will miss the round-2 variant; reviewers must probe mutators, not just constructors, and verify copy claims against the module they describe.
